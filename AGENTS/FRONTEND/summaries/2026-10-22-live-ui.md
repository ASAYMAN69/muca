# Summary — The live agent UI: session sidebar, streaming timeline, inline permission, policies, and help

**Status:** complete
**Date:** 2026-10-22

The judge-facing product from round 1 is intact (the timeline, the artifact
cards, the MCP evidence, the demo mode, the approval card) and is now a
real product: a session sidebar, a live streaming timeline driven by the
socket in `AGENTS/WS_PROTOCOL.md`, a permission card that explains itself,
a policies screen, and a help document that explains every control.

## What changed

### New modules

- `apps/web/lib/live.ts` → the socket client (§1–§5). The URL is derived
  from `window.location` (`/api/v1/ws?session=…&lastSeq=…`), so there is
  no host, no port and no environment variable in the source or the
  bundle. It tracks `lastSeq`, buffers a frame that arrives early until
  the hole in front of it is filled, asks the server to `resume` when it
  sees a gap, reconnects with a jittered exponential backoff and asks for
  everything it missed, and reports a `gap` frame so the app can refetch
  the session over REST.
- `apps/web/lib/live-run.ts` → a pure reducer from frames to run state.
  A permission request names the *request*, not the call, so the reducer
  ties it to the tool call that is still open; that is what keeps the
  timeline at one row per call.
- `apps/web/lib/format.ts` → `Intl`-based relative times, durations and
  session titles.
- `apps/web/lib/consequences.ts` → the plain-English sentence on the
  permission card, derived from the tool definition and the arguments,
  never from the model's prose. Plus the sentence that says what “allow
  and remember” will remember.

### New components

- `app/components/session-sidebar.tsx` (R1) → the sessions, newest first,
  each with its title, its age and a **needs you** marker when the agent
  is waiting. Clicking a session switches the whole view and opens a new
  socket for it; a new-session button sits at the top; it is a sheet below
  768px.
- `app/components/permission-card.tsx` (R4) → the inline permission card:
  the tool's own title and description, the exact arguments, a sentence
  saying what will change, the reason it is asking, and three actions
  (**Allow once**, **Deny**, **Allow and remember**) with the remember
  rule spelled out under the button.
- `app/components/policies-view.tsx` (R5) → the policies screen: the
  default in plain language, the list with tool, matchers, effect, scope
  and label, enable/disable, delete (with a confirm), and a form to create
  a policy with argument matchers, an effect and a label. The preview is
  a sentence: *“If you allow this, `create_branch` will run without asking
  you, when `name` starts with “fix/”.”*
- `app/components/help-panel.tsx` (R6) → the help document: what Muca is
  and is not, every control, every tool (from `GET /api/v1/tools`), what
  the approval system does, what to do when it asks you something, and how
  to read the timeline. One click from the sidebar footer and from the
  header.
- `app/components/thinking-row.tsx` (R3) → the live thinking row: alive
  while the model reasons, collapsed to a summary when the turn ends.

### Changed

- `app/page.tsx` → the new shell: the sidebar, the header (session title,
  the MCP pill, the help button, the live/request-response state), the
  policies view, the help drawer, the live client, the demo mode, and the
  run list. A run is now built from **either** the live frames **or** the
  request/response response, so there is one timeline for both.
- `app/components/timeline.tsx` → renders the permission card, the
  clarification step (with an answer field and optional choices), the
  thinking row and the new palette.
- `app/components/mcp-panel.tsx` (R7) → the panel is now a **status pill
  in the header** (connected · protocol · tools · session id) that
  expands on demand into the evidence: the handshake, the catalogue and
  the raw JSON-RPC traffic. It is evidence, not the product, and it no
  longer takes a third of the page.
- `app/globals.css` → the palette. **Dark is the default**, and it is
  designed rather than inverted: a warm graphite base (hue 70, almost no
  chroma) so it does not read as the usual observability blue, one mint
  accent for “live”, and a small semantic set for the states the timeline
  shows. The light theme is a designed counterpart and is opt-in
  (`?theme=light`).
- `app/layout.tsx` → the theme bootstrap (applied before the first
  paint), the skip link, and the `viewport` export.
- `lib/api.ts` → the sessions, policies and tools clients, plus the
  `clarification` events and the permission metadata on
  `confirmation_required`.
- `lib/timeline.ts` → **extended, not rewritten**: the existing fold of a
  call into its approval row and the second-pass status decision are
  untouched. It gained the clarification step, the permission metadata,
  and `inFlightCallIds` so a call that is still running reads *running*
  and not *failed*.
- `app/components/artifact-card.tsx`, `run-history.tsx` → the new palette.

## Decisions / trade-offs

- **One timeline, two sources.** The live frames are mapped onto the
  existing `AgentEvent` union, so a live run and a request/response run
  render through the same code and the same tests. The socket is additive:
  `POST /api/v1/chat` and `approvedCallIds` are unchanged, and the app
  falls back to them when the socket cannot be opened. The header always
  says which mode it is in (*“live, over the socket”* or *“one request at
  a time”*).
- **Dark is the default, and the light theme is opt-in.** A theme
  switcher is explicitly out of scope, and the system preference is the
  only other signal — honouring it would contradict “dark is the default”.
  So the light theme is a complete, designed theme that a link can open
  (`?theme=light`), linked from the help panel. If the coordinator wants
  the light theme to follow the system instead, it is one block in
  `globals.css`.
- **The permission card is the only place a decision is made.** It is
  inline, never a modal, and it is rendered by the same component in live
  and request/response mode. “Allow and remember” needs the socket (the
  server creates the policy from the decision), so in request/response
  mode the card says so instead of pretending.
- **The tool catalogue comes from the server.** The permission card, the
  help panel and the policy form all read `GET /api/v1/tools`; nothing is
  hardcoded.
- **The MCP evidence collapsed into a pill.** The handshake is still
  there, one click away, with the same session id, tool catalogue and
  raw JSON-RPC log.
- **The view and the help panel live in the URL** (`?view=policies`,
  `?help=1`), so they can be linked to.

### The socket is not on the server yet

The BACKEND agent is still building the socket, so the live behaviour was
driven against **a local mock of the protocol**, outside the repository:
`/tmp/opencode/mockws/server.mjs` (a `ws` server that speaks §1–§5 and
serves the §11 session and policy routes, proxying everything else to the
real app server on `:8111`). What was verified **against the mock**:

- the socket connects to `/api/v1/ws?session=…`, the `hello` frame
  arrives, and the client is *live*;
- a live run streams: thinking → tool call → evidence → permission →
  the decision → the outcome;
- the tool row appears **before** the tool finishes and reads *running*;
- the permission card renders once, with the tool description, the exact
  arguments, the consequence and the reason;
- **a dropped connection loses nothing**: the socket was killed
  server-side, the client reconnected on its own, asked for the frames it
  missed, and the timeline after the reconnect was identical to the
  timeline before the drop (same rows, the permission card still there);
- the demo mode, the policies screen, the help panel, the session
  switch, the new-session button, the light theme, the phone layout and
  the keyboard-only path.

What was **not** verified against a real server: the real
`/api/v1/ws` handshake, the real `lastSeq` replay, the real
`permission_requested` payload and the real policy routes. The client
follows `AGENTS/WS_PROTOCOL.md` exactly, and the unit tests cover the
sequencing, the gap handling and the reconnect.

**Everything else ran against the real server** (`PORT=8111
NODE_ENV=production npx tsx src/index.ts`): the app, the MCP handshake
(the real session id, 10 tools, the raw JSON-RPC log), the artifact
cards, the run history, `GET /api/v1/tools` and `GET /api/v1/health`.

## Follow-ups / risks

- **The socket is the only unverified part.** When the BACKEND agent's
  server is up, the one thing to re-run is the live flow: the frames, the
  `permission_requested` payload and the replay. The client was written
  to the protocol, not to the mock.
- **`permission_requested` carries no call id.** The protocol gives the
  tool call a `callId` and the permission a `requestId`, and they are not
  guaranteed to be the same. The client ties a request to the tool call
  that is still open, which is right for the common case (one open call)
  but would need the protocol to carry the call id if the server ever
  asks about a call that is not the most recent one. Worth flagging to
  the coordinator: adding `callId` to `permission_requested` would remove
  the guess.
- **The chat request has no session id.** `POST /api/v1/chat` keeps its
  contract, so the server has to work out which session a chat belongs to
  (a header, or the most recent socket). The client cannot say.
- **`GET /api/v1/sessions/:id` is not used for the timeline.** The
  timeline is rebuilt from the frames the server replays, which is what
  the protocol intends. The session route is used for the title and the
  waiting requests.
- The root `npm test` still runs only the server workspace; the
  coordinator has to add `@adh/web`.
- The BACKEND agent was editing `apps/server` and `AGENTS/BACKEND/`
  throughout; I did not touch them, and nothing was committed.
